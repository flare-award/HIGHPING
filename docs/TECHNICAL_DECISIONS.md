# Технические решения Latency Studio

## 1. Целевая среда и UI

- **.NET 10 / WPF**, Windows 10 x64 и Windows 11 x64.
- Публикация `win-x64`, self-contained, без trimming; поставка включает .NET runtime.
- WPF отвечает за интерфейс, пользовательские настройки, управление жизненным циклом и трэй.
- `LatencyStudio.Core` не зависит от Windows UI и содержит валидаторы, расчёты задержки, планировщик очереди, TCP-парсер и проверяемый контроллер жизненного цикла.
- `WinDivertRuntime` находится в Windows-приложении и использует P/Invoke только во время включения обработки.

## 2. Почему WinDivert, а не собственный WFP callout

Для реального задерживания локального системного трафика нужен перехват с удержанием и последующей повторной инъекцией пакетов.

- WFP — системная платформа фильтрации Windows. Простые WFP-фильтры умеют классифицировать и разрешать/блокировать трафик, однако корректная пользовательская очередь задержки и повторная инъекция для полного двунаправленного потока обычно требуют WFP callout-драйвера, WDK, подписания/развёртывания kernel-компонента и отдельного протокола с пользовательской службой.
- **WinDivert 2.2.2** уже предоставляет NETWORK-layer перехват и `WinDivertSend` для повторной инъекции исходящего и входящего IPv4/IPv6-пакета. Официальная поставка предоставляет подписанный x64-драйвер для Windows 10/11 и автоматически загружает его по вызову `WinDivertOpen`; сам вызов требует администратора.
- Поэтому выбран WinDivert, а не самописный WFP-драйвер: меньше собственного kernel-кода, меньше операций установки, доступны готовые документированные API перехвата и reinjection. Это не устраняет риск потери пакетов при аварийном завершении: в момент ожидания часть пакетов находится в пользовательской очереди.
- WinDivert бинарник и драйвер не модифицируются. Сборка скачивает официальный релиз по фиксированной версии, сверяет SHA-256 архива, DLL, SYS и LICENSE, а также скачивает и сверяет соответствующий архив полного исходного кода. Бинарные компоненты, текст лицензии и source ZIP помещаются в установщик/ZIP. Программа не скачивает драйвер во время работы.

## 3. Перехват и повторная отправка

- NETWORK filter: `!loopback and !impostor`. Loopback не задерживается; уже инъецированные impostor-пакеты не захватываются повторно. Сеть приложения и WinDivert работают на IP-уровне для системного трафика, не привязываясь к процессу.
- Содержимое пакетов и контрольные суммы не изменяются. При reinjection передаются оригинальные байты, направление и metadata интерфейса из `WINDIVERT_ADDRESS`.
- Receive loop и scheduler — отдельные долгоживущие worker-потоки. Время планируется по монотонному `Stopwatch` (QPC), ожидание событийное, без высокочастотного опроса.
- Ограничение очереди: до 8 192 пакетов и 64 МиБ. При переполнении пакеты очереди того же направления отправляются немедленно в порядке захвата, затем без задержки отправляется новый пакет. Это предпочитает отсутствие искусственной потери перед сохранением выбранной задержки.
- При штатном выключении WinDivert перестаёт захватывать новые пакеты; capture loop дочитывает уже накопленную native-очередь до `ERROR_NO_DATA` и передаёт эти пакеты без ожидания. Затем scheduler отправляет накопленную user-mode очередь и закрывается WinDivert handle. Принудительное завершение процесса не может гарантировать доставку пакетов, уже удерживаемых пользовательской очередью.
- Исключения TCP/UDP-портов проверяются в пользовательском режиме, поэтому их можно менять без переоткрытия нативного фильтра. Исключения по PID/имени процесса не реализованы: NETWORK layer не предоставляет владельца процесса.

## 4. Режимы задержки

### Фиксированный режим

Для каждого перехваченного внешнего IP-пакета применяется заданная задержка направления. 40 мс в исходящем и 40 мс во входящем направлении дают ориентировочно 80 мс к RTT для симметричного request/response. Счётчик или оценка не заменяют фактическую задержку: каждый перехваченный пакет удерживается до срока в очереди.

### Целевой RTT

Универсально узнать RTT произвольного UDP/QUIC-потока без протокольной семантики невозможно. Целевой режим поэтому не выдаёт предположение за измерение:

1. Для нового TCP-соединения фиксируется реальное время от исходящего SYN до входящего SYN-ACK.
2. Если ранее к исходящему SYN была применена известная задержка, она вычитается из handshake sample.
3. Для измеренного TCP-потока остаток `max(0, target − baseline)` делится пополам и применяется к направлениям.
4. Пока измерения нет, TCP-поток пропускается без искусственной задержки. Уже открытые до запуска потоки, UDP/QUIC/ICMP не получают target-калибровку; для них предназначен фиксированный режим.
5. Измеренные потоки хранятся ограниченно и очищаются по сроку жизни.

Это калибровка по TCP handshake, а не обещание того, что игровой/приложенческий RTT во всех серверах станет ровно заданным числом.

## 5. Измерения и честные подписи

- **Исходная задержка** — TCP SYN/SYN-ACK базовая оценка тестового узла или отдельного калиброванного потока.
- **Добавленная задержка** — конфигурационная оценка: сумма фиксированных направлений либо остаток целевого RTT для известного baseline.
- **Фактический RTT тестового соединения** — измеренное время установки TCP-соединения до выбранного host:port. Оно включает активную искусственную задержку, если обработчик включён; оно не включает TLS/HTTP и не является универсальным игровым ping.

## 6. Привилегии, фон и восстановление

- Основной UI запускается с `asInvoker`. UAC запрашивается только при включении перехвата, если приложение не повышено. После согласия приложение штатно перезапускается повышенным процессом.
- Автозапуск выключен по умолчанию и задаётся через HKCU `Run`. `--tray` запускает UI скрытым; задержка остаётся выключенной.
- Закрытие окна по умолчанию скрывает его в трэй; команда полного выхода в трее выключает обработчик, освобождает очередь и закрывает handle.
- В аварийном завершении Windows закрывает native handle и больше не применяет фильтр; пакеты, которые уже находятся в user-mode queue, могут потеряться. Абсолютное исключение потери при принудительном убийстве процесса невозможно.
